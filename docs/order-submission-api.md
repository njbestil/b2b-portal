# Order submission (#62)

`POST /api/v1/order-drafts/:id/submit` requires customer draft-management authorization, JSON `{ "version": "draft-..." }`, and exactly one `Idempotency-Key` header. The key is 1–128 printable ASCII characters without spaces. A successful request returns 202 with the portal order ID. The order's integration status indicates whether the initial ERP attempt succeeded or failed; 202 alone does not indicate ERP acceptance. A conflicting key, changed draft, failed validation or changed acknowledged price returns 409. Invalid input returns 400. Authentication and tenant ownership are enforced, and provider identifiers and messages are not returned in the submission response.

The service reads the current Mock catalog before taking database locks. Under the order transaction it rechecks the actor, session, draft version, delivery address, product mapping, validation and acknowledged prices using that snapshot. The external source offers neither a reservation nor a versioned atomic read with PostgreSQL; catalog values can change again after the read. The reservation, transition, immutable snapshots, audit entry and outbound request are committed together. The provider request is made only afterward. Mock object property order can change in JSONB, but item order and exact decimal strings are retained, which are the Mock contract's identity rules.

A PENDING transaction is claimed once before network I/O. The retained outcome is SUCCESS or FAILED; an ambiguous transport, malformed response, conflict or timeout is recorded as OUTCOME_UNKNOWN without automatic retry. A worker interruption after claim leaves PROCESSING, which must be reconciled rather than resent. Repeated portal submissions reuse the reservation and never resend a claimed request. Terminal business rejections are retained as sanitized codes. Order business status remains separate from integration status. Retry policy and operational reconciliation are future work; this implementation cannot guarantee exactly-once ERP effects.

The claim updates the integration transaction and the order's technical status to PROCESSING in the same database transaction. If either update fails, both remain PENDING and no ERP request is sent. Finalizing the attempt updates only the technical status and ERP reference, never the order's business status. A concurrent business transition is preserved. A technical-status mismatch fails closed for reconciliation.

The Mock ERP ledger is in-memory and disappears on restart. It is only enabled for development and test. Production and JSON-backed submission return unavailable: production requires a real authoritative provider with durable idempotency or reconciliation, and JSON requires an equivalent durable atomic boundary. Migrate PostgreSQL explicitly before using the endpoint; migration 0009 enforces one initial submission transaction per order. Review existing `ORDER_SUBMISSION` rows for duplicates before applying it.
