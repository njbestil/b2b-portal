# Draft commercial terms (#55)

The customer must review and acknowledge server-observed prices before a draft can pass validation. These mutable draft terms are separate from the immutable submission snapshots in #56. Existing drafts have no acknowledged baseline and receive `COMMERCIAL_TERMS_REQUIRED` until acknowledged. New or changed item identity/quantity also requires a fresh acknowledgement; changes to delivery address alone do not invalidate the line terms.

An authenticated active customer who owns the draft calls `POST /api/v1/order-drafts/:id/terms` with exactly `{version}`. It reads the live provider under the same authority and version checks as #54 and returns `{draftVersion,issues,terms,stock,token}`. `terms` is a list of portal item ID, product ID, quantity, exact unit-price amount and currency; `stock` provides current available quantity or null for each available item; `token` binds the prices and quantities to the draft/version. Stock is informational and may change without invalidating the token. If current prices are unavailable, `terms` and `token` are null and the validation issues explain why. The token is not an authorization credential, stock reservation or submission guarantee.

After reviewing the displayed terms, the customer calls `POST /api/v1/order-drafts/:id/terms/acknowledge` with exactly `{version,token}`. The server fetches the provider again and accepts only a token matching the current terms and unchanged owned draft; it stores its own terms, never client-supplied prices, and advances the shared draft version. A stale draft or changed quote returns `ORDER_DRAFT_CONFLICT`. A lost response or post-commit audit failure is uncertain: reload before acting rather than replaying automatically.

`POST /api/v1/order-drafts/:id/validate` continues to recheck live price and stock. A differing amount or currency yields `PRICE_CHANGED` with the portal item ID; equivalent decimals such as `1.0` and `1.00` compare equal. The consumer can request the current terms and require acknowledgement again. Stock changes are actionable only when stock is unknown (`STOCK_UNKNOWN`) or insufficient (`INSUFFICIENT_STOCK`); sufficient changes do not block. The existing validation issues still apply. These decisions were delegated by the user for #55.

The provider is the existing development/test synthetic Mock ERP source. Production remains unavailable without a real authoritative provider. A preflight is not a reservation: #62 must revalidate live values and guard the actual submission transition. The SQL migration adds a nullable draft baseline on the order; JSON stores it with the order in the existing atomic replacement. Neither records a submitted snapshot, mutates ERP, creates an idempotency key, or removes private order history.
