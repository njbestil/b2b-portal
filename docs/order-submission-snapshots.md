# Transaction-bound order snapshots (#56)

This is an internal component for future submission work, not a customer endpoint or a submission transition. `createOrderSnapshot` builds a detached, frozen version-1 record from already authorized and validated server-owned values. It retains order/company identity, submitting user ID/name/role, delivery identity and contact fields, product/SKU/name, selling UOM, MOQ, exact quantity, unit price, currency, line totals and total. Totals use exact decimal arithmetic without implicit rounding or currency conversion. Foreign-company actor/address, duplicate lines, invalid quantities and mixed currencies fail closed; only explicit fields are projected.

`withPostgresOrderSnapshot` owns a SQL transaction and passes its client to a trusted callback. The future submission service must revalidate authority, draft version, acknowledged prices, current product/stock/address and idempotency inside its boundary, perform its own order transition using that client, and return the server-built snapshot. The component checks the transitioned order identity, time, empty snapshot fields and matching item identities/quantities; writes order and item snapshots, exact prices and totals; and commits once. An exception rolls back the transition and all snapshots. The callback must not commit independently or call ERP inside this database transaction. A successful record is write-once through this component; existing snapshot evidence cannot be overwritten.

`commitJsonOrderSnapshot` uses the shared single-process security coordinator and one atomic `orders.json` replacement. Its trusted callback must return the proposed transitioned order and server-built snapshot; the component checks unchanged identity, delivery, lines, prior commercial baseline and draft version, validates the snapshot, rechecks the caller-supplied authority guard immediately before publication, and publishes transition and snapshot together. Callers must not recursively acquire the coordinator. Unknown private order fields refuse publication instead of being dropped. JSON remains a disposable single-process store, with its existing crash/durability limits.

Neither component is connected to an application route or used as an authorization decision. #62 must integrate live revalidation, the actual transition and the retained idempotency contract before using it. #57 owns idempotency and #62 owns ERP publication. A retry after an uncertain result must inspect retained state rather than blindly create a replacement. Existing order/invoice IDs and the ordinary order summary projection are unchanged. SQL uses existing snapshot columns; no migration is added.
