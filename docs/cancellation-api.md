# Cancellation requests (#76)

`POST /api/v1/companies/:companyId/orders/:orderId/cancellations` requires a normal authenticated Customer Admin, Customer User, or currently assigned Sales Staff member, one `Idempotency-Key` header, and exactly `{ "reason": "..." }`. The reason is trimmed, required, at most 500 UTF-16 code units, and cannot contain controls or unpaired surrogates. Keys are 1–128 printable ASCII characters without spaces. Success returns HTTP 202 with the portal request ID, order ID and `PENDING`, `APPROVED` or `REJECTED`; ERP references, upstream messages and customer references stay private. A matching key and request replays the same record; conflicting reuse returns 409.

Customers are scoped to their active company; a Sales request requires a current active primary assignment. Drafts remain creator-owned. Delivered, cancelled and rejected orders cannot start a new cancellation. A draft or pending-confirmation order with no submission can be cancelled directly. A submitted order whose ERP transaction is still PENDING can be directly cancelled only while atomically stopping that transaction. A PROCESSING or ambiguous submission without an ERP link cannot be cancelled directly. A linked submitted, confirmed or fulfilling order sends the cancellation to ERP for a decision. The frozen requirements do not make a delivered order eligible; the owner chose to block it.

PostgreSQL locks the current company, actor, session, assignment and submission transaction before the order. Request identity, reason, audit and the cancellation record commit together. The ERP request is durably retained and claimed once before network I/O. The service validates the complete Mock correlation and rechecks current authority, order state and ERP linkage before applying a decision. An approved decision changes the business status to CANCELLED; a rejected decision preserves it. Neither changes an already sent order's technical integration status. A changed order or linkage after sending is left for reconciliation rather than overwritten.

An unavailable, timed-out, malformed, uncorrelated or interrupted ERP result is not automatically retried: Mock receipts disappear on restart. The request stays pending and a duplicate key cannot send it again. A failure after a remote decision can require reconciliation. Production uses no Mock gateway; linked cancellation needs a real provider before it is available. Notification delivery remains #92 and is not implied by the audit records.

Migration `0010_cancellation_idempotency.sql` adds the PostgreSQL key binding. Cancellation reasons and provider payloads are private and must not appear in customer order summaries, logs or diagnostic responses. JSON implements the same command/status surface through the recoverable order, audit and one-attempt boundary described in [json-cancellation-recovery.md](json-cancellation-recovery.md). Its unlinked/in-flight submitted orders remain refused; only PostgreSQL can prove and stop a not-yet-claimed submission transaction. Review the recovery boundary before merge/shared enablement.
