# Bounded Mock submission retries (#64)

For the development/test Mock submission integration, `ERP_SUBMISSION_MAX_RETRIES` sets additional attempts after the initial call (default 2, range 0–5); `ERP_SUBMISSION_RETRY_DELAY_MS` sets the first delay (default 1000 ms, range 100–5000). Delays double for each additional attempt and are capped at 30 seconds. Invalid settings fail startup without echoing their values. Production submission and JSON-backed submission remain unavailable.

The adapter recognizes only the Mock's documented, correlated no-effect responses: 500 `ERP_TEMPORARY_FAILURE`, 503 `ERP_UNAVAILABLE`, and 504 `ERP_TIMEOUT`. Each response must match the retained external reference, portal order and customer. These fixture responses explicitly guarantee no order was created. A network deadline, uncorrelated or malformed response, unrecognized error, or failed database update is uncertain and is never retried. Business rejections are terminal. An HTTP 504 with the correlated Mock `ERP_TIMEOUT` receipt is distinct from a client timeout without a receipt.

Before each additional call the service atomically consumes one retry allocation and persists its scheduled time against the already claimed transaction. Retries reuse a detached copy of the same request identity and exact commercial values. The existing dispatcher stores the final result; reaching the limit records the last sanitized technical code and does not schedule another attempt. No raw provider message is exposed.

Retries run in the current dispatch worker. A process interruption, lost database acknowledgement, or other uncertain boundary leaves the transaction for reconciliation; no worker automatically reclaims PROCESSING, including after a scheduled delay. This favors duplicate prevention over automatic crash recovery. The Mock ledger remains process-local and cannot prove deduplication across restart. A production provider must offer durable idempotency or reliable reconciliation before production submission or retries are enabled. #63 separately owns synchronization of the order's technical status; no business status is changed by this retry wrapper.
