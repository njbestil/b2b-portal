# Reorder API (#59)

`POST /api/v1/orders/:id/reorder` accepts exactly `{}` and returns 201 with `{draft,items,issues,prices}` in the normal authenticated, no-store envelope. The ID selects a non-draft order in the admitted customer's company; Customer Admin and Customer User may reorder any such company order, including one created by a colleague. The new draft is owned by the requesting user. Sales and internal roles cannot use this endpoint. Foreign and missing orders return the same 404. No caller-supplied company, items, prices, role, or delivery selection is accepted.

The source must have a valid immutable submitted snapshot. Legacy orders without one return 409; corrupted or inconsistent evidence returns 503. The new order has fresh order and item IDs, no submitted snapshot or commercial acknowledgement, and no selected delivery address. Source quantities and product IDs are copied; historical prices are not applied as current prices. Current source data revalidates customer and product eligibility, selling UOM, MOQ, price and stock. `issues` uses the draft validation codes and identifies new draft item IDs. `prices` has `{itemId,previous,current,currency,changed}` using decimal strings and nullable current values. An unavailable, ineligible, below-MOQ or insufficient-stock line remains editable in the new draft and is reported; creating a draft is not authorization to submit it. A null current price is not silently replaced by a historic one. Current evaluations are point-in-time, not reservations; the existing submission checks and commercial acknowledgement still apply.

The provider must be configured and available. 400 covers invalid bodies, 401/403 admission, 404 missing/foreign/draft source, 409 unavailable legacy snapshot, and 503 unavailable provider/storage or unconfirmed audit. Do not automatically retry an uncertain mutation: audit happens after persistence, so a 503 may accompany a committed draft. Existing draft rate limits, JSON limits and session checks apply.

PostgreSQL locks the company, account, session, source order, product and existing access rows and commits the new header and all lines together. JSON uses the existing shared security coordinator and one `orders.json` publication. Both leave the source order and snapshot untouched, and recheck authority before commit/publication. This preserves the existing order storage boundary for cancellation work (#76); neither reorder nor its draft changes transitions the source's status. The upstream catalog snapshot is read before entering the write boundary, so stock and pricing may change after it is read; submission revalidates them again.
